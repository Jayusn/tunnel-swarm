# LDOP 设计总结

## 1. 为什么要做 LDOP

`LDOP` 的长期目标，是成为整个自主系统中的“动态环境感知模块”。

它未来应该承担的职责是：

- 读取原始 LiDAR 点云和里程计
- 区分静态信息和动态信息
- 跟踪动态目标并预测它们的运动
- 给 `rog_map` 提供更干净的静态点云输入
- 给规划器或后续融合层提供动态风险信息

这意味着 `LDOP` 不应该去替代 `rog_map`。

更准确地说，`LDOP` 应该成为：

- 让 `rog_map` 的静态地图更干净的模块
- 让规划器具备动态障碍感知能力的模块

## 2. 和论文思路的对应关系

论文《Flying through cluttered and dynamic environments with LiDAR》的整体流程，与 `LDOP` 未来的发展方向高度一致：

1. 定位 / LIO
2. 动态环境感知
3. 地图构建
4. 规划与控制

这篇论文对 `LDOP` 最重要的启发，是它把环境表示拆成了两层：

- 静态层
- 动态层

论文中的关键思想是：

- 静态层只使用静态点来构建
- 动态层使用动态目标未来的预测位置来构建
- 规划时同时考虑静态层和动态层
- SFC 生成时只依赖静态环境

这正好支持我们当前的架构选择：

- `LDOP` 负责动态感知与预测
- `rog_map` 负责静态占据、膨胀和 ESDF
- 规划器或后续融合层负责把静态风险和动态风险结合起来

## 3. 推荐的模块边界

### LDOP 应该负责什么

- 运动点检测
- 静态点 / 动态点分离
- 动态点聚类
- 跨帧目标关联
- 速度估计
- 短时轨迹预测
- 发布静态点云、动态点云和动态目标预测结果

### rog_map 应该负责什么

- 静态占据地图更新
- 障碍膨胀
- ESDF
- 静态碰撞查询
- 静态地图相关可视化

### 规划器或融合层应该负责什么

- 从 `rog_map` 查询静态安全信息
- 从 `LDOP` 查询动态风险信息
- 把两者组合成最终的规划代价或约束

## 4. 为什么“两个下一步”要一起做

之前确定了两个重要下一步：

1. 让 `LDOP` 输出 `static_cloud + dynamic_predictions`
2. 设计一套以后各模块都能自然使用的消息接口

这两件事应该一起做，原因是：

- 如果只发布点云，不设计目标级消息接口，后续规划器接入会被拖慢
- 如果只先设计消息，不接进真实节点逻辑，接口很容易和代码实际结构脱节
- 两件事一起做，架构设计和代码状态可以保持一致

可以把这条原则记成一句话：

- `LDOP` 每增加一个能力，都应该同步暴露成稳定的 ROS 接口

## 5. 当前 LDOP 的运行结构

当前 `LDOP` 的骨架已经按四层结构拆开了：

- ROS 回调层
- 处理线程
- 发布线程
- `AsyncSpinner`

### 当前数据流

1. 点云回调快速接收最新点云
2. 里程计回调维护最新位姿信息
3. 处理线程总是消费队列中的最新一帧
4. 发布线程发布处理结果

这种结构很适合作为低时延动态感知的基础，因为它避免了把重计算直接塞进 ROS 回调里。

## 6. 当前已经对外发布的接口

### 已有输出

- `/ldop/raw_cloud`
- `/ldop/odom`
- `/ldop/static_cloud`
- `/ldop/dynamic_cloud`

### 新增的动态预测接口

- `/ldop/dynamic_objects`

消息类型为：

- `ldop/DynamicObjectArray`

配套消息类型为：

- `ldop/DynamicObject`

这套消息接口未来打算承载的信息包括：

- 目标 id
- 目标中心位置
- 目标尺寸
- 目标速度
- 短时间范围内的未来预测位置

当前 `ldop/DynamicObject` 已经直接把预测信息收敛到两个数组字段里：

- `prediction_time_offsets`
- `predicted_positions`

这两个数组按下标一一对应，不再单独使用 `PredictedState` 消息。

目前仍处于骨架阶段，所以这个消息当前会发布“空数组”，等以后真正实现检测、跟踪和预测之后再填入真实内容。

## 7. LDOP 应该怎样和 rog_map 连接

### 第一阶段：先把静态建图做好

做法是：

- `LDOP` 输入：原始点云 + 里程计
- `LDOP` 输出：`/ldop/static_cloud`
- `rog_map` 输入点云话题：改成 `/ldop/static_cloud`

这一步已经能解决一个很重要的问题：

- 动态目标不容易在静态地图中留下 ghosting 残影

### 第二阶段：让规划具备动态感知能力

这一阶段继续保留：

- `rog_map` 作为静态占据和 ESDF 的提供者

新增：

- 规划器订阅 `/ldop/dynamic_objects`

然后利用动态预测来：

- 惩罚未来碰撞风险
- 调整参考路径搜索
- 对快速目标更早触发重规划

### 第三阶段：如果以后需要，再加融合层

如果后面系统复杂度上来，可以再单独做一个融合层，专门负责融合：

- `rog_map` 的静态占据 / ESDF
- `LDOP` 的动态预测

这种做法通常比一开始就把动态预测逻辑深度塞进 `rog_map` 更稳，因为模块边界更清晰，也更容易调试。

## 8. 推荐的开发顺序

### 第一步

先在 `LDOP` 里实现真正的静态点 / 动态点分离。

目标输出是：

- 有实际意义的 `/ldop/static_cloud`
- 有实际意义的 `/ldop/dynamic_cloud`

### 第二步

实现“动态目标”这个更高层的抽象。

目标输出是：

- 聚类后的目标
- 包围尺寸
- 速度估计
- 稳定的目标 ID

### 第三步

实现短时轨迹预测。

目标输出是：

- 带未来状态的 `ldop/DynamicObjectArray`

### 第四步

让规划器同时接入两类信息：

- `rog_map` 提供静态安全信息
- `LDOP` 提供动态风险信息

## 9. 一句话记忆法

以后如果要快速回忆整个设计，可以记住这句话：

`LDOP` 负责告诉系统“什么东西在动、它将往哪里去”；`rog_map` 负责告诉系统“哪些静态空间是安全的”。
