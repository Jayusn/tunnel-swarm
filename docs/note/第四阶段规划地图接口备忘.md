# 第四阶段规划地图接口备忘

这份文档记录一次阶段性结论，方便以后推进第四阶段“规划可用的膨胀地图或 ESDF / 风险地图”时快速恢复上下文。

## 核心结论

如果目标是给规划器用，主路径应学习 `ROG-Map` 的“内部地图 + 查询接口”思路；如果目标是地图共享和 RViz 可视化，应学习 `UFOMap` 主分支的 `ufomap_msgs/UFOMapStamped` 发布链路。

也就是说：

- 规划主路径：优先提供高频、批量、低开销的地图查询能力。
- 地图发布与可视化：发布标准 `UFOMapStamped`，让 `ufomap_rviz_plugins` 或外部节点消费。
- 当前帧输出语义：继续保持 `/ldop/static_cloud` 和 `/ldop/dynamic_cloud` 是当前帧动静态点云，不把它们误当作完整地图。

## ROG-Map 和 UFOMap 的区别

### ROG-Map 风格

`ROG-Map` 的核心地图保存在进程内部，规划相关能力主要通过 C++ 查询 API 使用，例如：

- `isOccupied(pos)`
- `isLineFree(start, end)`
- `boxSearch(...)`
- 膨胀障碍、未知区域、ESDF 等规划友好表达

它的 ROS 输出主要是给 RViz 看的局部点云或 `MarkerArray`，如 `rog_map/occ`、`rog_map/unk`、`rog_map/inf_occ`、`rog_map/esdf`、`rog_map/map_bound`。这些输出来自内部地图的局部查询结果，不是完整、可反序列化的地图状态。

因此，`ROG-Map` 更像“地图在内部，ROS 只发布可视化切片”。

### UFOMap 主分支风格

`UFOMap` 主分支的 `ufomap_mapping` 会发布 `~map` 和可选 `~map_depth_X`，消息类型是 `ufomap_msgs/UFOMapStamped`。

这个消息是完整 UFOMap 的二进制序列化，包含 unknown、free、occupied 和 metadata。`ufomap_rviz_plugins` 的 RViz Display 也订阅同一个 `UFOMapStamped` topic，并在 RViz 里反序列化后显示。

因此，`UFOMap` 更像“地图发布和 RViz 可视化共用同一个地图消息”。

## 规划器能不能直接调用 UFOMap

可以，但前提是规划器进程里必须有一个 UFOMap 对象。

不能做的是：一个独立的规划 ROS 节点直接访问 `LDOP` 节点内部的 `runtime.map`。两个 ROS 节点通常是两个进程，内存不共享。

所以“直接调用 UFOMap”有三种实际形态：

### 1. 规划器自己建图

规划包直接依赖 UFOMap，自己创建 `ufo::map::OccupancyMap`，自己插入点云，自己查询地图。

这当然可行，但它会和 `LDOP` 各维护一份地图。动静态分割、参数、清图、`seenFree`、label 等状态容易不一致。除非规划器完全不需要 `LDOP` 的动静态语义，否则不建议作为主路线。

### 2. 规划器订阅 `/ldop/ufomap` 后本地查询

`LDOP` 负责维护地图并发布 `/ldop/ufomap`，类型为 `ufomap_msgs/UFOMapStamped`。规划器订阅后，在自己的进程里反序列化成本地 UFOMap 对象，规划时直接调用 UFOMap API 查询。

这个方式适合高频规划：

- `LDOP` 维护唯一的地图语义。
- 规划器本地保留地图副本。
- 碰撞检测、采样检查、轨迹优化等高频查询不跨 ROS 通信。
- ROS 只负责同步地图，而不是参与每一次查询。

代价是需要处理地图同步、更新频率、序列化/反序列化开销，以及规划器持有地图副本后的延迟问题。

### 3. 规划器和 LDOP 同进程

把规划模块和 `UfomapMapper` 放在同一个节点进程里，通过稳定的 C++ 查询接口直接访问同一份地图。

这是性能最好的方式，但耦合最高。只有在服务接口和本地地图副本都无法满足实时性时，再考虑这条路线。

## 推荐给 catkin 规划包的接入路线

### 近期路线：LDOP 提供批量查询服务

先给 `LDOP` 增加面向规划器的 service，而不是让规划包直接碰 `UfomapMapper` 内部对象。

建议的服务形态：

- `/ldop/query_points`：批量查询点的 occupied / free / unknown / seenFree 状态。
- `/ldop/check_lines`：批量线段碰撞检查，用于轨迹边或采样边。
- `/ldop/query_local_obstacles`：查询局部 box / sphere 范围内的 occupied voxel 或动态候选。
- 后续如果构建 ESDF，可增加 `/ldop/query_esdf`。

注意：服务必须是批量接口。规划器不应每个点单独调一次 ROS service，否则通信开销会压过地图查询本身。

这种方式的优点是 catkin 边界清楚：

- 规划包只依赖 `ldop` 的 `.srv` / `.msg`。
- `LDOP` 仍然拥有唯一地图状态。
- 后续 `UfomapMapper` 内部怎么演化，不直接破坏规划包。

### 中期路线：发布 `/ldop/ufomap`

补齐 `UFOMap` 主分支风格的地图发布：

- topic：`/ldop/ufomap`
- type：`ufomap_msgs/UFOMapStamped`
- 用途：完整地图共享、RViz 插件显示、高频规划器本地建副本

这条链路不替代 `/ldop/static_cloud` 和 `/ldop/dynamic_cloud`。两路点云仍然保持当前帧动静态点云语义；累计地图状态由 `/ldop/ufomap` 表达。

### 长期路线：稳定 C++ 查询接口

如果第四阶段需要更强实时性，可以在 `ldop_core` 内形成稳定查询接口，例如：

```cpp
bool isOccupied(const ufo::Point& point) const;
bool seenFree(const ufo::Point& point) const;
bool isLineFree(const ufo::Point& start, const ufo::Point& end) const;
std::vector<UfomapCandidateNode> queryLocalOccupied(...);
```

这类接口必须明确读写锁边界、坐标系假设和参数语义，避免规划线程和建图线程互相踩状态。

## 对第四阶段的设计提醒

第四阶段不应只问“发布什么 topic”，而应先问规划器需要哪类查询：

- 点查询：当前位置是否安全。
- 线段查询：轨迹段是否穿过障碍。
- 局部障碍查询：规划范围内有哪些 occupied voxel。
- 距离查询：离最近障碍多远，是否需要 ESDF。
- 时序风险查询：动态目标未来位置是否影响某个时间点的轨迹。

静态层和动态层要保持可分离：

- 静态层来自第一阶段稳定后的 UFOMap 静态地图。
- 动态层来自第三阶段动态目标预测。
- 动态风险可以参与 planning map / risk map 融合，但不应永久写进静态地图。

## 当前项目应保持的边界

- `Ldop` 负责 ROS I/O、线程调度和对外发布。
- `UfomapMapper` 负责 UFOMap 插入、`seenFree` 判别、当前帧动静态点云分割、节点查询和 label 等基础能力。
- `/ldop/static_cloud`：当前帧静态点云。
- `/ldop/dynamic_cloud`：当前帧动态点云。
- `/ldop/static_map_markers`：当前阶段的 RViz 可视化辅助输出。
- `/ldop/ufomap`：后续应补齐的完整 UFOMap 地图发布 topic。

## 一句话备忘

第四阶段给规划器用时，查询接口学 `ROG-Map`，地图共享和 RViz 链路学 `UFOMap`；`LDOP` 自己维护地图语义，规划包通过批量服务或 `/ldop/ufomap` 副本使用它。
